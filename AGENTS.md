# EnergiOS working rules

- Read `docs/EnergiOS_PRD.md` and `docs/EnergiOS_Backend_Implementation_Plan.md` completely before coding. The PRD controls product scope, claims and API shapes; the Implementation Plan controls task order. Code, tests, real data and deployment evidence determine completion; a plan alone does not.
- Inspect the repository and `git status` before each task. Preserve teammate files, commits and uncommitted work. Work only on the next unchecked P0 task unless explicitly directed otherwise. Do not advance past a failed data, security or deployment gate.
- Prototype scope rule: Treat the 20-item checklist as a triage list, not a requirement to complete every item. Implement only agreed P0 items needed for the working EnergiOS hackathon MVP. Real-data forecasting and a grounded chatbot are now explicitly agreed product scope, gated by the plan. Defer full authentication implementation unless required by approved data-access rules, separate staging infrastructure, Sentry, plugins/MCP setup, a formal design-system document, solar simulation and multi-agent AI unless explicitly requested. Do not begin P1/P2 features automatically.
- Keep the PRD and backend implementation plan unchanged unless the agreed product scope, API contract, technology stack or deployment architecture changes.
- Current implementation is a minimal Python 3.12 FastAPI service; the real-data MVP is planned. Until authorised Sime Darby data is available, an explicitly approved, traceable public measured dataset may be used as a provisional benchmark for backend and energy-model work. Building Data Genome Project 2 (BDG2) v1.0 is the currently approved fallback. It is **not** Sime Darby or Elmina Lakeside Mall data and must never be presented as site-specific evidence. Export `app` from `backend/app.py`. `/health` must return exactly `{"status":"ok","version":"1"}`. `/docs` documents only implemented routes.
- Use one shared repository and separate Vercel projects rooted at `backend/` and, once ready, `frontend/`. Confirm repository ownership, import access, target team/project and plan eligibility before deploying. Do not create or publish a remote repository without team approval.
- Before changing backend API contracts or handing them to the frontend team, check the latest accessible frontend commit. Compare its API requests, field names, units and status handling with the PRD and the current backend OpenAPI schema; report every mismatch and any unavailable frontend evidence. Preserve teammate files and commits, and coordinate contract changes instead of overwriting their work.
- No Supabase, analytics or chatbot libraries until the authorised task's data/deployment gates pass. The tiny production deployment is verified; a separate Preview is not yet verified. Do not fabricate `/v1` endpoints, database results, credentials or integrations.
- The submitted MVP must never use synthetic, fabricated, AI-generated or invented operational data in its database, ML training, frontend charts or demo. Preserve Task 3 files as historical internal test fixtures only; do not load their SQL into the submitted database or claim real-data model/product performance from them. Older seed-loading instructions are superseded by the real-data PRD and plan.
- A public measured fallback must be pinned to an official release, cited and licensed for the intended use, and retain source/version/checksum, transformation, units, timezone, reading semantics and limitation evidence. Label its output `Public benchmark data` and name the dataset. Do not relabel it as corporate, township, mall, floor, room or equipment data.
- Store and preserve real-data provenance, source, permitted use, units, timezone, reading semantics and limitations. Require a reviewed non-destructive provenance migration plan before real import; the existing synthetic-only schema is not real-data compatible.
- Clearly distinguish observed, forecast, detected, estimated, proposed, approved and verified results. Financial/carbon/savings outputs require explicit sources, assumptions and estimate labels. Verified savings require a documented intervention, baseline and post-action measurements. Carbon neutrality is a long-term ambition, never a guaranteed result.
- Do not invent missing readings, HVAC causes, tariff rates, carbon factors, savings, room performance or sensor data. ML predicts energy consumption or demand; documented tariff rules calculate cost. Whole-building readings support building-level analytics only. Do not enable room, floor, HVAC, solar, battery, EV, indoor-condition or live-control features unless real supporting measurements/mapping and approval support them; live control requires separate explicit authorisation.
- BDG2 supports provisional whole-building benchmark work only. Its current inspected files do not establish Elmina asset identity, township coordinates, floor/room/equipment mapping, operating schedules, HVAC causes, Malaysian tariffs, Malaysian carbon factors, interventions or verified savings. Unsupported outputs remain unavailable.
- Keep restricted real data, real environment files, credentials, chatbot API keys, generated data and local tools out of Git history, frontend bundles, logs and chat. Supabase secrets/admin tokens and chatbot keys belong only in approved backend environment settings. Sanitise errors and public responses; an open demo may expose real data only with explicit publication permission.
- Future database errors must fail explicitly, never substitute fabricated data. Missing energy intervals remain missing. Floor meters must not double-count an authoritative building total.
- From `backend/`: `uv sync --locked`, `uv run --locked pytest`, and `uv run --locked uvicorn app:app --host 127.0.0.1 --port 8000`.
- Require relevant tests before completion claims, actual deployed endpoint checks before deployment claims, and verification against the real frontend before compatibility claims. Before handoff, report exact changed files, test evidence, deployment state and unfinished work. Local success does not prove Vercel compatibility. A documentation-only task does not authorise an import, migration, deployment, commit or push.
- Keep source documents and implementation status distinct. Record evidence in `docs/preflight-status.md`; never mark planned features built without verification.
